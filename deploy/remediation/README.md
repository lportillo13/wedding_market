## Origin restrictions

It fetches current ranges from Cloudflare's documented public IP API, validates each network, and allows those sources plus loopback. The ACME challenge path stays outside the restriction. API requests forwarded by Cloudflare are limited to five per second per visitor, with a burst of 20; ordinary pages and static assets are not rate limited. An existing global real-IP rewrite or changed site layout causes a safe stop for review.

The tool saves the old site, validates `nginx -t`, and reloads. Configuration failure restores the original. After execution, verify the public domain in a browser, the direct-origin rejection from outside the server, and a certificate renewal dry run. ## Encrypted data copies

owner-backup-setup.py --r2-only installs Ubuntu's signed age encryption package and an independent, pinned Node runtime under /usr/local/lib/wedding-market-backups. That directory is root-owned; the deploy-owned application cannot supply executable code to the root timer. Existing credentials are read in memory, and only the Wedding Market R2 bucket is listed/read. No remote object is deleted. Each object and its manifest are encrypted in the standard age format, immediately decrypted to a hashing sink, and compared with the source digest. The recovery identity stays in /etc/wedding-market-backups/identity.txt, root-only. Store an independent recovery copy yourself; never paste it into chat.

A successful first copy enables wedding-market-backup.timer daily at 05:20 UTC with random delay. Copies stop if the free disk reserve is below five GB or twice the current object size. Encrypted ciphertext is exported to the audit account for an off-host copy; neither credentials nor the recovery identity are included. Copies currently accumulate until the owner reviews retention. Failed or incomplete directories are retained for inspection and do not count as a successful backup. Monitor systemctl status wedding-market-backup.service and available disk space.

It does not include database cluster roles, other managed schemas or a server image. An isolated restore into a suitable Supabase target is still necessary; archive inspection alone does not prove full recovery.
